## 0. 一句话结论

**99.96 与本数据的所有证据冲突，必须先确认量纲再决定是否把它当目标。** 四条独立证据（元数据上限 0.751、无序号泄漏、无重复图、错误结构由"标签边界模糊"主导）一致指向：本赛题 AUROC 的现实天花板在 **0.98–0.99**，而非 0.9996。更关键的是，**本项目历史上已经发生过一次同类误抄**：用户最初报告的"99.02"曾被写成 0.998，实际是 **0.9902**（`WB/可行方案1可行性评估.md` 第 14 行已记录该更正）。"99.96"与"99.02"只差 0.94，很可能是同一显示口径下的两个相邻数值，而不是从 0.9902 跳到 0.9996。**在确认前，以 0.9902 作为追赶基准，不要按 0.9996 配置资源。**

另一个必须立刻修正的认知：**现有三折 OOF 存在患者级泄漏**，60.9% 的 holdout 图像其同患者另一只眼在训练折里，Green 的 0.9542 真实值约为 **0.945–0.948**。

## 1. 已确认的事实

### 1.1 数据结构（此前未知，最重要）

| 事实 | 数值 | 证据 |
|---|---:|---|
| train / valid / test 行数 | 51,396 / 5,849 / 5,855 | CSV |
| 阳性率（train / valid） | 3.224% / 3.266% | 1,657 / 191 |
| 年龄缺失 | train 10 个，valid/test 0 个 | CSV |
| **同年龄连续块** | 27,231 块，其中 22,192 块长度恰为 2 | 结构分析 |
| 推定患者数（代理） | 27,959 | 块内两两配对 |
| 块内标签一致率 | **96.62%** vs 随机基线 93.76%（z=18.1） | 23,437 对 |
| 阳性中"对侧眼为阴性"比例 | **47.8%** | — |

**含义**：CSV 按患者排序，每患者 1–2 张图（绝大多数 2 张，同年龄）。标签是**逐眼**标注而非逐患者，因此不能用"患者级标签"假设。但同患者两眼确实共享 3 个百分点的标签相关性，这足以构成泄漏通道。

### 1.2 患者泄漏的定量后果

| 指标 | 数值 |
|---|---:|
| holdout 中"对侧眼在训练折"的比例 | **60.86%** |
| Green OOF 全体 | 0.9542 |
| Green OOF，泄漏子集（n=31,278） | **0.9585** |
| Green OOF，干净子集（n=15,596） | **0.9457** |
| 差值 | **+0.0128** |
| P1 fold0，泄漏子集（n=10,374） | 0.9710 |
| P1 fold0，干净子集（n=5,212） | 0.9763 |

分折看：fold0 0.9555/0.9533、fold1 0.9609/0.9450、fold2 0.9612/0.9430。
判读：泄漏效应在 Green 上方向一致（三折中两折明显），量级 +0.005～0.013；单折层面各自不显著（SE≈0.005–0.008），但方向一致且机制清楚。P1 上方向相反且不显著，说明**大容量全微调模型的分数并非主要来自患者记忆**——这是好事，意味着模型选择没有被泄漏严重扭曲。

**处理决定**：不为本次比赛重建折划分（会使全部历史结果失去可比性，且全量重训代价不可接受）。改为：(a) 所有跨模型比较继续使用同一折，相对结论有效；(b) 报告一律标注"含患者泄漏的乐观估计"；(c) 最终用官方 valid 做一次无偏确认。

### 1.3 元数据捷径确实存在，但远不足以解释 99.96（S1）

分组交叉验证（GroupKFold=5，按患者代理分组）：

| 实验 | 输入 | OOF AUROC | OOF AUPRC |
|---|---|---:|---:|
| S1-A | 仅年龄 | 0.6577 | 0.0624 |
| S1-B | 仅图像统计量（尺寸/字节/亮度/裁边） | **0.7188** | 0.1062 |
| S1-C | 仅文件序号 | 0.4767 | 0.0301 |
| S1-D | 全部元数据 | **0.7509** | 0.1163 |

单变量最强：年龄 0.6683，bytes_per_pixel 0.4315（反向），res_code 0.5537。
分辨率族共 **49 个**，阳性率跨度 **1.4%–9.6%**（如 4752×3168 为 9.59%，2736×1824 为 1.43%），相差 6.7 倍。

**含义**：设备/采集来源与标签强相关，这是真实存在的捷径，且因为 train/valid/test 同分布（见 1.4），它会**原样迁移到测试集**。但它单独只能到 0.75。合理用法是作为**辅助特征或分层变量**，不是主线索。

### 1.6 R1 排序错误结构：错误由"假阳性"主导，且高度集中

| 指标 | 数值 |
|---|---:|
| 逆序对总数 | 3,774,354（错误率 4.58%） |
| 中位阳性被多少阴性超过 | **495 / 49,739（1.0%）** |
| 阳性中分数低于 neg_p95 的比例 | 22.2% |
| 阴性分数前 10% 贡献的逆序占比 | **60.0%** |
| 分数 >0.02 的 3,619 个阴性贡献的逆序 | **51.5%** |
| 分数 >0.005 的 7,972 个阴性贡献的逆序 | **72.9%** |

阴性分数十分位（由低到高）对应的逆序占比：0.1%、0.4%、0.7%、1.1%、1.8%、3.1%、5.4%、8.9%、18.4%、**60.0%**。

反事实上限：
- 把 >0.02 的 3,619 个阴性全部正确压到最低 → AUROC **0.9778**
- 把 >0.005 的 7,972 个阴性全部正确压到最低 → AUROC **0.9876**

**含义（这是本次审计最重要的可操作结论）**：阳性找得已经很好，瓶颈是**一小撮"看起来像青光眼"的阴性**。任何能把这 4,000–8,000 张图区分开的机制，价值远大于"提高分辨率找更多阳性"。

### 1.7 高分阴性是什么：标签边界模糊，不是模型缺陷

| 阴性分层 | n | 中位年龄 | 对侧眼为阳性的比例 |
|---|---:|---:|---:|
| 全体阴性 | 49,739 | 57 | 1.6% |
| 分数 <0.005 | 41,767 | 56 | 0.66% |
| 0.005–0.02 | 4,353 | 61 | 3.77% |
| 0.02–0.1 | 2,358 | 62 | 7.59% |
| **>0.1** | **1,261** | **63** | **13.64%** |

全体阳性中位年龄 63。即：高分阴性在**年龄**和**对侧眼标签**两个维度上都与阳性同分布，富集倍数 20 倍。

人工目视 8 张（`WB/audit/hard_cases/hard_sheet.jpg`）：
- 上排 4 张"最难阳性"（分数 ≈0）：视盘外观接近正常，杯盘比不大，无明显神经视网膜缘缺损。
- 下排 4 张"最高分阴性"（分数 ≈0.999）：**杯盘比明显增大、神经视网膜缘变窄，形态上符合青光眼**。

**含义**：这批阴性更可能是"青光眼疑似/早期"被标为 0，或标签口径为"确诊"而非"疑似"。这不是模型能通过更好训练解决的问题，它给 AUROC 设了硬上限。**任何"困难负样本挖掘"或"排序损失"若不区分真噪声与真病变，会主动教模型忽略真实病变——必须谨慎。**

### 1.8 部署：模型不是瓶颈，预处理才是

| 项目 | Green ft2 | RFM P1 |
|---|---:|---:|
| 参数量 | 21.8M | 64.4M |
| 输入 | 392（784 tokens） | 336（441 tokens） |
| **FP16 纯前向 p50（batch=1, 4060 Laptop）** | **14.0 ms** | **18.4 ms** |
| 纯前向 p95 | 15.8 ms | 25.5 ms |
| 峰值显存 | 156 MB | 417 MB |
| 端到端 p50（已有测量，含读盘/解码/裁边/缩放） | **120.4 ms** | — |

端到端 120ms 中，**约 106ms 是 I/O + JPEG 解码 + crop_fov + 缩放**，前向只占 14ms。已有诊断：解码裁边中位 44.4ms、缩放 21.1ms。

**已定位到一个具体缺陷（实测）**：`decode_image` 的 draft 目标是 `max(1024, size)`。JPEG 的 DCT 缩放档位只有 1/1、1/2、1/4、1/8；对 2592 宽的图，1/2 = 1296 > 1024，PIL 因此**保持全分辨率解码——`draft` 实际是空操作**。同一张 `test_00000.jpg` 实测：

| draft 目标 | 实际解码尺寸 | 解码 | 裁边+缩放 | 合计 |
|---|---|---:|---:|---:|
| 无 / 1024（现状） | 2592×1944 | 23.5 ms | 34.0 ms | **57.5 ms** |
| 512 | 1296×972（1/2） | 10.7 ms | 12.6 ms | **23.3 ms** |
| 392 | 648×486（1/4） | 6.5 ms | 5.7 ms | **12.2 ms** |

**含义**：
1. 100ms 约束的战场在预处理，不在模型选型。当前 Green 端到端 120ms 已超限，但把 draft 目标从 `max(1024,size)` 改为按 `size` 取值即可省 **35–45ms**，端到端落到约 75–85ms。这是**确定性可得的收益**，优先级高于任何建模改动。
2. 代价：draft 改变了下采样链路（2592→648→392 vs 2592→392），像素会有微小差异，必须重跑"32 张缓存前后一致性 + 预测最大差 <0.001 + AUROC 差 ≤0.0005"检查后才能上线。
3. **双分支/ROI 方案在部署上是可行的**——它不增加解码次数，只增加一次 crop+resize+前向（约 +20–30ms），而预处理优化已腾出 40ms 空间。
4. 模型体积：Green 87MB、RFM 258MB，两模型集成 345MB，**在 500MB 内**；三模型会超。

### 1.9 训练侧：现有配置明显欠训练

P1 第 6 轮（最后一轮）即最佳轮，训练 loss 仍单调下降（0.1290→0.0974→0.0764→0.0623→0.0529→**0.0466**），没有收敛迹象。Green ft2 同样是第 6/8 轮最佳。backbone_lr=1e-5 + cosine(T_max=epochs) 对 ViT 全微调偏保守，有效批量仅 32。

### 1.10 融合被严重低估（零成本已验证）

在同一 fold0 holdout（17,132 张 / 552 阳性）上：

| 方案 | AUROC | AUPRC |
|---|---:|---:|
| Green ft2 单模型 | 0.95481 | 0.59809 |
| RFM P1 单模型 | 0.97335 | 0.71269 |
| 概率 50/50 | 0.97073 | 0.69630 |
| **logit 50/50** | **0.97510** | 0.71999 |
| logit w_green=0.3 | **0.97614** | 0.72343 |
| rank 50/50 | 0.97271 | 0.70144 |

两模型 Spearman 仅 **0.62**，最难阳性集合重叠率 **98.2%**（难例相同、易例互补）。

**含义**：把一个 0.955 的模型加进 0.973 的模型，白得 **+0.0018（等权）～+0.0028（w=0.3）**。这是目前单位算力收益最高的动作，且完全不需要训练。

## 4. 当前最优主路线及选择依据

**主路线：RFM 全主干微调（全局）为性能核心 + Green 全微调为互补成员 + logit 等权融合 + 预处理优化保部署。**

选择依据（按证据强度排序）：

1. **容量/全微调是唯一被验证的大幅增益**：RFM 全 FT 相对 Green 末 2 层同折 +0.0185。而分辨率从 441→784 tokens 反而下降，说明当前阶段"模型容量 + 解冻深度"比"像素数"更值钱。
2. **融合是已验证的免费增益**：+0.0018～0.0028，两模型相关性仅 0.62。
3. **分辨率/ROI 假设未被证伪但也不是首要矛盾**：错误集中在"高分阴性"，而高分阴性的问题是**语义模糊**而非**看不清**——把图放大 2 倍不会让一个"疑似"变成"确诊"。ROI 路线应排在容量与融合之后。
4. **部署约束不构成架构否决**：前向 14–18ms，瓶颈在预处理；双分支仍可做，但不是现在的优先项。
5. **99.96 不可追**：四条独立证据一致。

**明确放弃**：把"困难负样本挖掘/排序损失"作为主攻方向。理由：R1 显示高分阴性与阳性在年龄、对侧眼标签上同分布，且目视确认形态符合青光眼——强行压制会损伤真阳性。若要做，只能作为"温和正则"，λ≤0.1，且必须以"高分阴性组的 AUROC 不下降"为否决条件。

### E1（第一优先）：Green 全主干微调 @392，fold0

**核心假设**：Green 当前只解冻末 2 层（+norm），其 0.9548 是"表征被冻结"造成的，而非容量不足；全主干微调 + 合理层间学习率衰减可显著逼近 RFM。

**为什么是第一**：唯一能在不触碰 RFM 预算的前提下检验"容量/解冻"这一最强证据链的实验；复用现有 392 缓存（零缓存构建成本）；同折、同 seed、同缓存、同增强，是干净的 A/B；无论成败都产出可用的融合成员。

**配置**（`WB/experiments/green_full_ft.json`）：

```json
{
  "model": "green", "size": 392, "use_age": true, "head": "linear",
  "tail_blocks": -1,
  "epochs": 10, "batch_size": 4, "accumulation": 8,
  "head_warmup_epochs": 1,
  "backbone_lr": 0.00003, "head_lr": 0.001,
  "layer_decay": 0.75,
  "patience": 3, "auto_pixel_cache": true
}
```

与 `green_ft2.json` 的差异仅三处：`tail_blocks` 2→−1、`epochs` 8→10、`backbone_lr` 1e-5→3e-5，新增 `layer_decay`。

**必须的代码改动**（`glaucoma/engine.py` 第 442–445 行）：当前优化器只有 backbone / head 两组，全微调时所有层共享 3e-5，深层会过冲。替换为按 block 分组的层间衰减：

```python
def _param_groups(model, config):
    base_lr = float(config.get("backbone_lr", 1e-5))
    decay = float(config.get("layer_decay", 1.0))
    head_lr = float(config.get("head_lr", 1e-3))
    blocks = list(getattr(model.backbone, "blocks", []))
    n = len(blocks)
    groups, seen = [], set()
    stem = [p for name, p in model.backbone.named_parameters()
            if p.requires_grad and not name.startswith("blocks.")]
    if stem:
        groups.append({"params": stem, "lr": base_lr * decay ** n})
        seen.update(map(id, stem))
    for i, blk in enumerate(blocks):
        ps = [p for p in blk.parameters() if p.requires_grad]
        if ps:
            groups.append({"params": ps, "lr": base_lr * decay ** (n - 1 - i)})
            seen.update(map(id, ps))
    rest = [p for p in model.parameters() if p.requires_grad and id(p) not in seen]
    groups.append({"params": rest, "lr": head_lr})
    return groups

optimizer = torch.optim.AdamW(_param_groups(model, config), weight_decay=0.01)
```

`CosineAnnealingLR` 会按 group 的 `base_lrs` 分别衰减，无需其他改动。`layer_decay` 缺省 1.0 时行为与原实现等价（向后兼容，不影响历史结果）。

**运行命令**：

```powershell
$python = (Get-Content runtime.local.json -Raw | ConvertFrom-Json).python
& $python -u run.py train --config WB/experiments/green_full_ft.json --fold 0 `
    --output artifacts/green_full_ft/fold0 --workers 4 --max-hours 3
```

**资源预算**：
- 显存：预计 3–5GB（ViT-S，784 tokens，batch 4）。若 OOM，在配置加 `"gradient_checkpointing": true`（速度降约 30%）。
- 耗时：现 Green ft2 为 340s/轮（含内部验证）；全微调反向成本约 2.5–3×，估 **650–850s/轮**，10 轮 **1.8–2.4h**。
- 磁盘：复用现有缓存，新增权重约 90MB。
- 无需追加 RFM 预算。

**晋级标准**（事前写定，禁止事后调整）：

| 门槛 | 条件 | 动作 |
|---|---|---|
| **G1 通过** | fold0 AUROC ≥ 0.9600（较 Green ft2 +0.0052） | 进入 E3 融合，补 fold1/2 |
| **G2 强通过** | fold0 AUROC ≥ 0.9650 | 升为全量重训候选，并评估替代 RFM 的可行性 |
| **G3 融合门槛** | 加入 RFM P1 后 logit 等权融合 ≥ 0.9765（较 P1 单模 +0.0032） | 进入最终提交候选 |
| **否决** | AUROC < 0.9600，或训练不稳定（loss 发散/NaN） | 停止，Green 保持末 2 层版本，资源转向 E2 |
| 附加否决 | 若 ≥0.9600 但融合增益 <0.001 | 不作为成员，仅记录 |

配对比较一律用图像级分层 bootstrap（1,000 次），区间跨 0 不表述为"提升"。

### E2：RFM @448 全主干微调，fold0

**核心假设**：在保持 ViT-B 容量的前提下把 token 数从 441 提到 784（视盘像素约 ×1.78），可获得分辨率收益。

**前提**：**需要用户批准追加 RFM 预算约 13,200s（3.7h）**。当前账本余 149.4s，脚本会直接抛 `Insufficient existing RFM budget`。28,800s 是自设上限而非赛事规则，追加属于用户决策，不自动执行。

**配置**：复制 `rfm_p1_global.json`，仅改 `"size": 336 → 448`、`"epochs": 6 → 8`、`"backbone_lr": 1e-5 → 2e-5`，其余（`native_resolution`、`view_version`、`gradient_checkpointing`）不动。位置编码由 `_rope_on_device` 按 `feat_shape` 动态生成，改尺寸是安全的——但必须跑一次实现检查确认 token 数为 784 且前向/反向正常。

**资源预算**：P1 实测 1,240s/轮 @336/441tokens；448/784tokens 约 ×1.78 → **2,200s/轮**，8 轮 **≈4.9h**。显存 P1 峰值 417MB，448 约 ×1.8 → 750MB，`gradient_checkpointing` 已开启，8GB 无风险。

**晋级标准**：fold0 AUROC ≥ 0.9760（+0.0027），且配对 bootstrap 下界 >0；否则判定分辨率无收益，RFM 停在 P1，资源全部转融合与部署。

### E3：三成员融合 + TTA + 嵌套权重选择（0.5h，0 训练）

**已验证起点**：Green ft2 + RFM P1 的 logit 等权 = 0.97510（+0.00175）；w=0.3 = 0.97614（+0.00279，但该权重是在同一 holdout 上选的，有选择偏差）。

**要做的三件事**：
1. **权重不在这份 OOF 上选**：用 fold0 内部的 5 折再切分做嵌套选择，外层 holdout 只做最终报告；或直接固定等权（0.97510 是无选择偏差的下界）。
2. **TTA**：`hflip` 已在训练增强中使用，属于安全 TTA；加 `hflip + 0.9/1.0/1.1 尺度` 共 6 视图，logit 平均。在 OOF 上先验证再决定启用。
3. **第三成员**：优先等同事 CNN 的 OOF；若仍未交付，用 Green full-FT（E1）或不同 seed 的 RFM 作为第三成员。三模型 logit 等权通常再 +0.001～0.003。

**部署核算**（必须同步做）：三模型体积 87+258+~90 = 435MB < 500MB，但需实测 FP16 前向总时延；若超 100ms，改为"RFM+Green 双模型"或对 RFM 做蒸馏。
